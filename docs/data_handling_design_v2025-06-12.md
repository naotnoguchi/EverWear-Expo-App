# Data Handling Design (Fast & Simple)

最終更新: 2025-06-12

このドキュメントは、ClothesManagerApp における **アイテム・ブランドデータの取得／更新方針**を確定させ、今後 AI エージェントへ修正指示を出す際のコンテキストとして利用する。

---

## 1. 要件まとめ

| 項目 | 要件 |
| --- | --- |
| オフライン起動 | 不要（オンライン前提） |
| リアルタイム同期 | 不要（他端末変更は即時反映しなくて良い） |
| パフォーマンス | 高速化優先（ただし件数は小規模想定） |
| 実装方針 | シンプルさ最優先、保守コスト最小化 |

---

## 2. データ取得ポリシー

### 2.1 ブランドデータ
- **取得タイミング**: アイテム追加画面・アイテム編集画面を開いた時に毎回 Supabase へ `SELECT id, name FROM brands ORDER BY name` を実行。
- **キャッシュ**: 一切行わない。`BrandCache` は今後削除しても良い（※段階的移行可）。

### 2.2 アイテムデータ
- **取得タイミング**
  1. アプリ起動時 (`ClothingProvider` マウント時) に全件取得。
  2. ユーザー操作で **作成・更新・削除**が成功した直後に、Supabase 応答を待って **全件再取得 (洗い替え)** 。
- **更新ロジック**: 楽観的に Context を更新しない。サーバー応答後に `refreshData()` を呼び**一括置換**する。
- **差分取得やページング**: 現状不要。データ件数が増加した場合のみ再検討。

---

## 3. フロー図 (更新時)

```
[ユーザー操作] ─▶ supabaseClothingService (add/update/delete)
         │                               │
         │<─────────── 成功応答 ────────┘
         ▼
ClothingContext.refreshData()  ← getClothingItemsWithHistory()
         ▼
       UI 再レンダリング
```

- **常にサーバーの真実の値**を表示するため、不整合が生じない。
- API 失敗時は UI が変わらず、追加ロジック不要。

---

## 4. 変更指針 (今後のタスク例)

1. **BrandCache 無効化 / 削除**
   - `getAllBrands()` を直接 Supabase へ問い合わせる実装に書き換え。
2. **Context 更新方式の統一**
   - `wearItem`, `washItem`, `addItem`, `updateItem`, `deleteItem` などで楽観的更新を削除し、各メソッド末尾で `refreshData()` を await する。
3. **リフレッシュ UI**
   - Home 画面の `pull to refresh` などでは `refreshData()` を呼び出すだけで整合する。
4. **不要コード掃除**
   - `updateItemInState`, `addItemToState`, `removeItemFromState` など部分更新専用ヘルパーは不要になれば削除。

---

## 5. 期待される効果と留意事項

- **メリット**
  - 状態不整合やロールバック実装の懸念が消え、コード量が減少。
  - 他端末で変更された内容を取得する場合でも、ユーザーがアプリを再起動 or 明示的にリフレッシュすれば反映。
- **デメリット**
  - ネットワーク往復を待つため、操作直後の UI 反映は若干遅くなる (小規模データ想定で許容)。
  - 大量データに拡張する場合は再検討が必要。

---

## 6. 今後のレビュー基準

- **全件洗い替え**で 500ms 以内に完了するデータ量を維持すること。
- 体感遅延が問題になる場合のみ、差分更新 or 楽観的更新への切り替えを再検討する。

---

以上が確定方針です。AI エージェントは本ドキュメントを前提に修正タスクを実施してください。
